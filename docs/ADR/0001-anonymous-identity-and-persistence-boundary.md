# ADR-0001：匿名身份与持久化边界

- 状态：Proposed（待产品与安全审批）
- 日期：2026-09-16
- 关联任务：MVP-0.1-T001
- 关联需求：PRD §2.3、§3.2、§5、§7.1、§10.4
- 审批依据：PRD 已批准匿名进入、注册后保留学习数据及重启恢复的产品约束；本文的具体认证和留存策略尚无额外审批，故保持 Proposed。

## 背景

MVP 必须让新学生用一句话直接开始学习，不以注册或画像问卷为前置条件；同时，画像、路径、学习单元和课堂进度要能在服务重启后恢复。PRD 已定义 `POST /api/auth/guest` 创建匿名学习会话，并要求注册后保留学习数据，但尚未固定匿名凭据、留存期限和升级冲突策略。

本 ADR 只确定 MVP 所需的身份与持久化边界。它不引入 P1 的 BYOK、跨设备匿名同步、Redis 会话缓存或账户合并功能。

## 提议方案

### 身份与认证

1. 客户端第一次进入时调用 `POST /api/auth/guest`；服务端创建一个 `users` 记录，`is_guest=true`，且 `email` 与 `password_hash` 为空。
2. 服务端签发只含不透明 `session_id` 的随机会话令牌，作为 `Secure`、`HttpOnly`、`SameSite=Lax` 的 Cookie 返回。令牌本身不携带学习内容、画像或可枚举的用户 ID。
3. 后续请求由该 Cookie 解析到匿名用户。浏览器 JavaScript 不读取令牌；不得把令牌写入 localStorage、URL、客户端日志或分析事件。
4. 匿名身份只在同一浏览器配置文件中延续。清除 Cookie、使用其他设备或无痕窗口不会自动恢复同一匿名身份；界面应在实现阶段以非误导性的文案说明这一点。

### 数据归属与隔离

1. 创建的临时画像、学习会话、学习单元、场景进度、答题/学习行为和已审核资源引用均以该匿名 `user_id` 归属并存入 PostgreSQL。
2. 业务查询必须从经过认证的身份派生 `user_id`；不得接收或信任客户端提交的 `user_id` 作为数据归属依据。
3. 对所有归属用户的数据读取、修改和 SSE 重连均执行所有者过滤。资源正文如可被多个单元复用，使用受审核的不可变资源记录；用户只能通过自己拥有的单元引用读取它。
4. 日志、指标和 Provider 调用只使用最小必要的伪标识及诊断数据；不记录 Cookie、完整学习输入、画像正文或 Provider 凭据。

### 重启恢复与删除边界

1. PostgreSQL 是匿名学习状态的唯一持久化来源；进程内内存只能保存短暂的请求/SSE 连接状态，不能作为学习状态的唯一副本。
2. 每次可恢复变更（例如创建学习会话、更新进度、写入正式资源版本）在向客户端确认前提交数据库事务。服务重启后，客户端以现有 Cookie 重新认证，并从数据库读取最后一个已提交快照。
3. 正在流式生成但尚未写入正式版本的内容，在进程中断后允许丢失；后续 ADR 将定义幂等键与恢复事件。未审核内容不得因恢复而转为正式资源。
4. P0 不承诺匿名数据的跨设备同步或永久保留。具体匿名数据 TTL、自动清理方式和“清除本设备学习数据”的用户入口为待决项；在审批前不得实现自动删除任务或作出永久保存承诺。

### 注册升级

1. `POST /api/auth/register` 在当前匿名会话已认证的前提下，将该 `users` 记录绑定到新账号凭据，并保留其现有关联数据，不复制到第二个用户记录。
2. 成功后服务端轮换会话令牌、撤销旧匿名令牌，并以已认证账号身份继续会话，降低会话固定风险。
3. MVP 只支持“当前匿名身份注册为全新账号”。若注册邮箱已存在、一个账户要合并多个匿名身份或用户要跨设备找回匿名数据，返回明确冲突/不可恢复提示；这些流程留待后续批准，不得静默合并。

## 状态转换

```text
无身份
  └─ POST /auth/guest → 匿名 user + Cookie
                              │
                              ├─ 学习行为 → PostgreSQL（按 user_id 归属）
                              ├─ 服务重启 → Cookie 认证 → 读取已提交快照
                              └─ POST /auth/register → 同一 user 绑定账号 + 轮换 Cookie
```

## 替代方案

| 方案 | 优点 | 不采用原因 |
| --- | --- | --- |
| 仅在浏览器 localStorage 保存匿名学习状态 | 无需服务端身份模型 | 无法满足 PRD §10.4 的服务重启恢复；容易暴露、篡改或在多标签页失步。 |
| 无 Cookie、由客户端每次上传匿名 UUID | 实现看似简单 | 客户端可伪造其他用户 UUID；不能提供可靠的数据隔离。 |
| 首次使用强制注册 | 可直接跨设备同步 | 违反 PRD §2.3 与 §10.4 的“一句话直接开始”要求。 |
| 将匿名身份仅放在 Redis/进程内 | 短期访问快 | Redis 属于 P1，且进程/缓存丢失不满足可恢复要求。 |
| 创建第二个正式用户并复制匿名数据 | 保留审计轨迹 | 复制容易产生部分失败、双写及所有权混乱；同一记录升级更简单可审计。 |

## 与 PRD 的对应关系

| PRD 条款 | 本 ADR 的落实 |
| --- | --- |
| §2.3 匿名进入、注册后跨设备同步 | 匿名 Cookie 立即可学习；注册在同一用户记录上绑定账号，账号之后再支持同步。 |
| §3.2 临时画像可逐步更新 | 临时画像由匿名 `user_id` 归属并写入 PostgreSQL；未知字段仍按 schema 保存。 |
| §5 数据模型 | 使用 PRD 的 `users.is_guest` 概念，关联学习数据一律由服务端所有者过滤。 |
| §7.1 认证 API | 为 `/api/auth/guest`、`/api/auth/register` 规定认证前提与升级语义。 |
| §10.4 服务重启可恢复 | PostgreSQL 保存已提交状态；Cookie 重新认证后恢复快照。 |

## 待决项与审批请求

以下内容没有在 PRD 中得到批准，本 ADR 不把它们视为已决定：

1. 匿名数据的留存时长、自动删除机制以及用户主动删除的范围与确认流程。
2. 会话绝对有效期、空闲超时、撤销列表存储及多标签页/多设备登录策略。
3. 账户已存在时，是否允许把当前匿名学习数据合并到该账户；若允许，需另行定义冲突、审计和数据最小化规则。
4. Cookie 的准确 Domain、是否需要 CSRF token，以及部署在同站点还是跨站点前后端域名下的策略。

这些选择会改变用户数据生命周期或认证安全边界，应在实现 T003/T004 前经产品与安全审批；在批准前，后续实现仅可遵循本文已提议的最小行为，不得自行扩展。

## 后果

- 后端需要可迁移的 `users`、会话和学习状态持久化模型，并在每个数据访问点执行所有者约束。
- 前端的首屏流程需能在无 Cookie 时先创建匿名身份，并在 Cookie 失效时提示重新开始或注册账号；不得承诺未注册数据可跨设备找回。
- 后续 API/SSE ADR 必须规定会话失效、重连、取消与幂等语义，并与本身份边界一致。
