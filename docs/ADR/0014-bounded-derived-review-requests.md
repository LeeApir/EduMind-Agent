# ADR-0014：T040 诊断中有界子请求的冻结与预算补充

- 状态：**Proposed，等待用户批准 A–D**；不是运行授权，未实施真实派生计数器或发送器。
- 日期：2026-10-15；关联任务 PHASE-1-T040。
- 本轮“继续”只用于完成本补充提案；真实 Provider 请求 **0**。
- 继承：[ADR-0011](0011-independent-dynamic-acceptance.md)、[逐条审核设计 ADR-0013](0013-claim-level-resource-review.md)、
  [零调用原型](../acceptance/phase-1-t040-claim-review-prototype/README.md)。不改原批准附件、历史结果或发布门禁。

## 现状与决定范围

ADR-0011 要求实际完整请求发送前冻结。逐条审核的覆盖、声明及修正请求依赖前一步的结果，
不能在第一次调用前就得到全部实际输入 hash。原型的 SQLite 只用于合成步骤，不是实际预算或调用授权。

现有 `phase1-run-v1` / `FrozenBudget` 的清单及 ledger freeze 均不可变；不能为每个子请求另造新根清单、
重置 ledger，也不能删除 input_sha256 检查来容纳未知正文。

推荐新增独立 `phase1-derived-diagnostic-v1` 契约与计数器：**批准固定范围与派生规则，
每个实际子请求在发送前另行固定正文与父证据，再从同一批准预算中原子预留**。
不是让模型自己决定下一步调用，也不是事后补批准。

本补充仅拟用于 T040 的历史资源诊断/独立校准。T040 正式新例、DSL、T041、生产流量不在此适用范围。
批准 A–D 仅允许实现和离线验证这里的机制；每个真实诊断组/校准轮次仍须另批模型、请求数、费用及准确根清单。
若不批准本补充，继续按现行规则在每个依赖阶段得到具体输入后重新冻结审批，不启用自动链路。

## A. 根清单及批准范围固定

真实运行前，受信组合层形成完整根清单并绑定人类批准记录的准确 digest。
人类批准来自实际用户决定，任意 JSON 的 approved=true、模型输出、文件名或父请求通过均不能产生授权。
设计附件中的 source hash 只是设计审阅依据，不充当未来尚未实现的代码版本。

| 必须预先固定的内容 | 约束 |
| --- | --- |
| 阶段/组/轮次 | diagnostic，唯一 run_id、独立组预算、病例固定顺序；不自动进入下一组或阶段 |
| 根样本 | 原候选、resource_type、完整参考上下文、原标签各自准确摘要与可信来源；不读正式新例调参 |
| 目标与配置 | 单一批准 Provider/目标/model、可得 revision、能力/传输、所有角色模板及 schema、采样/推理参数、代码/锁文件摘要 |
| 派生算法 | 字段分块/ID/排序/序列化/合并版本；各父子数据允许路径和输入字段；没有模型自选阶段 |
| 结构上限 | 每阶段的数组元素数、字符/字节深度上限、总 wire 大小、输入 Token 保守界、推理+可见输出上限 |
| 调用与费用 | 每案例/每组的潜在槽集合、实际尝试上限、微货币整数预算、单次及全流程期限、并发1、失败处理 |
| 前置与检查 | 目标接入证据、ADR-0008 同意/凭据/SSRF边界、原标签批准、各组先后及人工事实确认规则 |

API Key 不进入根清单/子记录。凭据由受信发送层使用批准的凭据版本解析；版本失效即停，不能静默换 Key/Provider。
如果 revision 不可得，明确 unknown；不能声称锁定不可验证的上游模型权重。响应身份不符或已知模型别名映射改变即停并重评证据。

**批准之后不得变化**：样本、模板、schema、模型配置、代码、价格上界、计数/金额/时间上限及派生路径。
任何变化都新建轮次重新批准；不能说“模型数据变了”而夹带新的系统指令。
当前没有完整根清单、目标参数或真实预算申请；本稿不批准 r09 请求。

## B. 允许派生的有限图与实际输入冻结

每个案例从 round=0 开始；诊断建议 corrections=0。只有具体真实计划明确批准 C=1 或2，才分配修正路径，C不得超过2。
全图的潜在槽及其最多一次尝试在批准前列明：

```text
(case,round).inventory
    → (case,round).coverage
    → (case,round).claim[01..K]（按服务端清单的固定顺序，逐条发送）
    → (case,round).overall
    → [仅合法 revise、完整流程完成且已批修正] correction
    → 下一 round 的 inventory
```

K 是批准上限，不是必须凑足的声明数量。覆盖补出的条目必须包含在同一个 K 内。
覆盖结束后才分配 claim ordinal：以每条声明排序后的首锚点路径、start、end、服务端 claim_id 排序，
序列化/字符排序规则版本预先固定；模型列表顺序不能直接成为发送顺序。空余 ordinal 不得重分配给其他资源。
整体检查发现新的清单外断言或冲突时停止，不临时加第 K+1 个审核、不递归调用覆盖检查。
无声明也必须完成提取、覆盖和整体检查。模型不能请求新增阶段、工具、外网访问、角色、模型或金额。

### 1. 父结果合格后才构造子请求

父响应必须已完成、模型匹配、schema/锚点/容量与数值用量有效，并已在 ledger 记账；
有未解决覆盖/协议/用量问题不能进入下一阶段。故障不能靠“先继续下一个再补证据”恢复。
每个子请求引用明确的父尝试集合：coverage 引用 inventory；每条审核引用 inventory+coverage 得到的最终清单；
overall 引用最终清单及全部已运行的审核收据；correction 引用完整合法聚合结果；下一 round 还引用 correction。
这些依赖引用用于控制/审计，不强制把所有其他审核结论塞进模型上下文，避免以先前 verdict 当标准答案。

对父响应分别记录：传输/解码观察 hash、**实际保留且经过校验的规范化结果 hash**、验证器版本、用量与完成记录。
原始响应和推理正文可不保存；不能声称能从脱敏结果重建原始 hash。
需要派生的可见结构化数据必须按既有安全边界保存并校验摘要；若因敏感回显而被丢弃，停止派生，不仅凭 hash 继续。
诊断保留数据不包括 Key、供应商错误正文、任意私有聊天；访问范围、保留/清理按现有验收材料规则，不扩展公开接口。

模型文本只放在预批模板的数据字段。系统指令、JSON schema、URL、采样参数和目标不从模型字符串生成；
不执行候选/模型代码，不允许字符串拼出新的工具或命令。规范化描述/相关锚点不准替换完整原候选与参考上下文。
修正只能改变已批准类型的候选 content；节点、上下文、语言等固定要求不能由模型悄悄更换。

### 2. 子请求在发出前固定

受信代码用固定模板和允许的数据字段序列化完整 wire，必须符合该阶段最坏输入/输出上界。
随后在同一 ledger 的原子事务中写入不可变 child record 并预留预算，提交成功才允许进入发送层。
组运行注册应在首个尝试之前完成：受信批准登记绑定唯一 run_id、固定规范 ledger 路径与不可替代的启动记录摘要。
子请求、模型数据和命令行覆盖不能另选路径。注册已存在但 ledger 缺失/不符时不得自动重新初始化。
以下数据不得事后修改：

- 根 manifest/人类批准 digest、case/round/stage/ordinal、服务端 claim_id（如有）、目标/config digest。
- 精确父尝试 ID、其保留结果 digest 集合，以及候选/上下文/最终清单 digest。
- 实际规范化 wire 的完整 bytes hash、stage template/schema/序列化版本、实际 bytes 长度和已证明的 Token 上界。
- 本次预留的计数、同币种微货币整数金额、单次及剩余整体期限。

本地请求摘要与实际发送的 bytes 必须相同。发送器核对出站 URL/Host/SNI、凭据同意版本、目标锁和现有 SSRF 规则；
不重定向、不隐式代理或自动重试。不能只把一条 SQLite 记录当成完整出站授权。
父引用为 DAG 边集合，不用“上一条响应 hash”冒充所有真实依赖；同案例不同 round 的旧清单/pass 不可代用。

## C. 同一预算的原子预留、并发与恢复

新增计数器与旧 v1 独立命名、schema 严格验证，不放宽旧 `FrozenBudget` 或恢复旧 ledger。
子记录与预算预留共用一个批准组账本；禁止每个子请求新建预算根或用不同 run_id 绕过累计上限。
每批准诊断组仅1个在途尝试，受信执行层同时仅允许一个活动组，组间人工门禁保持。

事务需一起校验批准/来源未变、父结果持久化完成、槽顺序、未被占用、计数/金额/期限有余量以及没有停止标记，
然后写 child record+reservation+唯一尝试 ID。任何校验失败都不能读 Key 或打开网络连接。
发送前尚未拿到完整 Token 用量不妨碍使用已证明上界预留；响应后未知/超界用量必须停止。
实际底层发送入口必须原子地把 RESERVED 变为 SEND_INTENT，一次转换只准当前调用发送一次；
同一尝试再次进入该入口应在网络前拒绝（包括同进程重复调用）。HTTP/SDK内部重试及流重连均须关闭，
不能仅在结果返回后发现 outbound_sends>1 才记错误；这些要求须通过并发与故障测试证明。

### 预算不能依赖实际结果“碰巧短”

批准前对每个阶段的最长合法输入建立有限上界：候选、参考上下文、全部声明/相关锚点、全部允许发现、
固定提示/schema、修正候选及序列化转义的额外尺寸均计入。字符串 maxLength 不等于 UTF-8 bytes，
嵌套 JSON/提示中的引号、反斜杠和控制字符转义也必须有保守上界；未证明则不能启动。
字节到 Token 的界限必须针对实际传输/模型成立，不能直接套用原型中的合成Token上限。

每轮一个币种；input/output price 为每百万Token的微货币整数，I为输入Token保守界，O为总输出Token上限：
`slot_cost = ceil(I * input_price / 1000000) + ceil(O * output_price / 1000000)`。
分项分别向上取整；价格按批准的保守峰值，不依赖缓存/优惠/时段折扣。无法证明价格或收费上界时禁止调用。

批准组预算至少覆盖最大可达计划槽的上述最坏费用和次数；含互斥分支时采用已证明的最大可达路径，
不能任意排除可能进入的修正轮。首版可保守按全部潜在槽预留上界证明，但不能对外称全部都会发送。
实际每槽可按最终 wire 证明的 I≤预批上界预留；失败不退预留，不用实际低账单解锁额外槽或资源。
未被需要的潜在 claim/修正槽标记为不适用，不冒充模型审核 pass；固定资源级分母不改变。

K=16时，单案例无修正最多19次；2次修正最多59次。这些仅为次数计算，不是本轮真实授权：

| 原诊断组 | 固定资源数 | C=0时潜在请求上界 |
| --- | --- | --- |
| 错误检出 | 5 | 95 |
| 分类 | 同5例重新发送 | 95 |
| 正确对照 | 1 | 19 |
| 长审核 | 2 | 38 |
| 合计 | 13条独立资源链 | 247 |

旧“13次”不能授权247次，旧约600次完整测试预算也不适用于该流程；金额必须由具体可执行根清单计算，不能用本表替代费用批准。

### 崩溃恢复与禁止重发

```text
父已验证 → CHILD_RESERVED（正文hash+父引用+预算已提交）
          → SEND_INTENT（持久化） → RESPONSE_OBSERVED → VERIFIED 或 HALTED
```

任何持久化 reservation 都消耗一次尝试与预留额度，包括“可能没发出去”的情况。
SEND_INTENT 不能证明供应商收到请求，网络返回也不能证明结果已持久化；不承诺跨HTTP/SQLite恰好一次发送。
恢复时存在 RESERVED/INTENT 或未完成响应的悬挂记录，一律停止为人工可核对的“发送/用量状态不确定”，
保留预留、不重发、不自动标成未运行。供应商可能已计费；不能用进程重启退预算。

只有所有先前尝试均已有完整合格收据、无停止标记、同一根/批准/来源/期限仍有效、且人工组门禁满足时，
才能恢复到下一条**从未预留**的合法槽。根清单必须给出固定 expires_at 和整体时限，启动时保存有效截止点；
进程内用单调计时限制等待，重启不得重新起算整体时限。时钟回退导致剩余期限无法可信核实时即停。
恢复不扩大截止时间，不自动唤醒，也不让模型决定恢复。
已经 HALTED 的组不能靠补写一个 pass 重新开始；新轮次需另批，原失败和未知尝试继续保留。
若账本丢失/损坏、hash不匹配或权限不安全即停，禁止删除账本后同轮重建；新路径也必须绑定原不可替代的run登记。

## D. 诊断事实门禁及实施准入

派生机制只解决“有限数据依赖如何先记账再发送”，不解决模型事实质量；提取+覆盖仍可能共同漏项。
既有根标签、指标、严重漏检/正确例误拒/协议/用量失败停止、各组人工事实确认及后续阶段独立批准均保留。
每资源汇总时核对其全部已批准具体缺陷的位置、类别和检出情况（队列例包括原两项），泛泛 revise 不是通过。
一条资源拆成N条声明不会增加正确样本数或冲淡漏检；未运行原资源留在原分母，旧r01–r08不拼入新成绩。
独立校准若采用少量历史例，也不能代替四组诊断或被解释为完整诊断通过。

单个声明返回符合预期的“发现缺陷”属于流程数据，不等于立即触发整个组失败；原事实门禁在该资源完成/失败时判定。
实际 Provider/预算/安全/协议/覆盖未知故障立即停，不等到整篇完成；正确对照的已核实重大错误断言也立即停止。
需要人工语义判断才能判定的错误，在展示具体可见输出并核对后停，不把自动粗判 null 改写成事实通过。
修正只在真实计划明确允许且整个候选可合法聚合为 revise 时触发；不可用、部分完成或事实门禁已失败时不修正重跑抵销旧失败。

实施顺序建议：

1. 批准本补充 **A–D** 及准确提案清单，只允许实现独立动态计数器/派生验证与合成出站测试。
2. 离线证明来源/父绑定/预算原子性/并发唯一性/停机恢复/恶意输出/真实边界不退化，不接入生产。
3. 形成准确目标、全部阶段提示与schema、有限输入证明、实际代码与依赖摘要、每组次数/费用和安全发送组合。
   校准/真实诊断根计划再由用户单独批准后才能读 Key 和发送。
4. 逐组实际运行并人工核对；完整T040、DSL、T041和正式开放仍走原独立门禁。

至少新增离线验证：额外阶段/厂商/模板注入、父结果伪造/重排/重放/跨候选、缺失必需父边、超长转义/整数溢出、
预留前崩溃/预留后崩溃/发送后收据前崩溃、竞争双发、未知用量、ledger替换/路径逃逸、旧v1拒绝动态清单。
原型当前的 hash 链与61测试不能冒称上述真实出站机制已经实现或通过。
