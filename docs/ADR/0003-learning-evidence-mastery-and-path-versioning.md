# ADR-0003：学习证据、掌握度与路径版本边界

- 状态：Accepted（MVP 0.2）
- 日期：2026-09-21
- 关联任务：MVP-0.2-T001
- 关联需求：PRD §3.2、§3.4、§3.7、§5.2、§5.4、§5.5、§9.1

## 背景

MVP 0.2 要把“输入→学习→练习→掌握度更新→下一步推荐”连成可恢复的闭环。其中，测验、提示、重新解释和用户反馈是已发生的事实；掌握度、画像和路径则是由事实和版本化规则得到的可变结论。

如果直接覆盖掌握度或画像，将无法解释推荐、安全重算、处理重复提交，也无法判断状态是由新证据还是新规则引起。本 ADR 固定 MVP 0.2 的事实、投影、版本与事务边界；具体表名和 API 字段由后续任务实现，但不得改变这些语义。

## 决定一：学习证据是只追加的事实

`learning_evidence` 是掌握度、画像和路径的共同事实来源。已提交证据不原地更新或删除；更正错误时追加带 `corrects_evidence_id` 的补偿证据，保留原始记录。每条证据至少包含：

- 服务端从认证上下文得到的 `owner_id`，不接受客户端声明的所有者。
- 稳定的证据 ID、`evidence_type`、服务端记录时间和用户行为时间（如果可信）。
- 知识节点 ID，以及适用时的学习单元、场景、已发布资源和资源版本引用。
- `schema_version`、决定该条标准化结果的规则版本，以及去敏后的结构化载荷。
- owner 范围的 `idempotency_key` 与规范化请求摘要；相同键且摘要相同返回原结果，摘要不同返回冲突。

P0 白名单证据的含义如下：

| 类型 | 服务端可信事实 | 允许的影响 | 不得视为 |
| --- | --- | --- | --- |
| `quiz_attempt` | 已发布题目版本、作答快照、服务端评分、逐题结果与错误模式 | 掌握度、薄弱点、路径 | 客户端上传的正确性或分数 |
| `hint_used` | 系统实际提供的提示级别和关联场景 | 掌握度风险、画像候选、路径 | 用户已掌握或未掌握的单独证明 |
| `reexplanation_requested` | 已接受的“更简单/更深入/换例子”等白名单动作 | 困惑风险、资源偏好、路径 | 自动扣分或事实性画像属性 |
| `explicit_feedback` | 白名单选项及关联对象，如喜欢解释、过难、过易、跳过、标记已会 | 画像、路径风险；仅规则明确允许时轻量影响掌握度 | “跳过”或“标记已会”直接产生 `mastered` |

前端停留时长、点击或回放只是分析事件，除非未来 ADR 明确升级为学习证据，否则不进入 P0 掌握度计算。Provider 输出可以提议画像更新，不能伪造行为证据、测验得分或掌握状态。

## 决定二：派生状态分层归属并保留版本

| 数据 | 归属与真实来源 | 版本语义 | 是否可重算 |
| --- | --- | --- | --- |
| 公共知识结构 | 系统级、版本化 YAML | 内容变化产生新 `graph_version` | 否；它是已审核事实源 |
| 学习证据 | owner 级、PostgreSQL 只追加记录 | 每条证据是独立事实 | 否；只能追加补偿证据 |
| 节点掌握度 | owner + 知识节点 | 每次有效变化创建不可变 revision；当前行是可替换投影 | 是，从有效证据按规则重放 |
| 节点状态 | owner + 知识节点，掌握度投影的一部分 | 与同一 mastery revision 同步 | 是，不单独写入 |
| 学生画像 | owner 级 | 每次有效合并创建不可变 `profile_version` | 可从画像事件重建；不覆盖历史快照 |
| 学习路径 | owner + 学习目标 | 每次有效规划或重规划创建不可变 `path_version` | 是，使用快照中记录的全部输入 |

掌握度保存 `score`（0–1）、`status`（`unseen` / `learning` / `weak` / `mastered`）、前后值、证据引用、`mastery_rule_version` 和 revision。状态只能由版本化阈值和证据规则推导，不允许 LLM 或客户端直接写入。

画像版本保存字段值、来源证据、置信度、合并规则版本和前一版本引用。未知字段保持未知；用户显式修正优先级高于模型推断。

路径版本保存目标、有序节点、当前/前置/下一节点、推荐理由，并固定 `graph_version`、`profile_version`、所用掌握度 revision 水位、`planner_rule_version` 和前一路径版本。理由必须指向前置关系、具体证据摘要或明确画像字段之一，不存储敏感证据原文。

## 决定三：评分、掌握度和路径均使用版本化确定性规则

- 客观题正确性由服务端根据已发布题目版本确定性评分。LLM 不决定对错。
- 掌握度权重、衰减、连续错题、提示/重新解释影响及状态阈值位于受版本控制的服务端配置。
- 路径权重、可达性、排序和并列规则位于受版本控制的服务端配置。并列时使用稳定节点 ID 作最终求值，保证相同输入得到相同路径。
- ProfileAgent 只生成结构化候选更新。本地 schema、证据允许列表、优先级和合并规则决定是否创建画像版本。

规则版本是不可变标识，不得将配置文件在原标识下静默替换。升级规则不重写旧证据或版本；如需应用新规则，显式创建新的 mastery revision、profile version 或 path version，并记录触发原因。

## 决定四：事务与失败边界

### 学习行为命令

一次会影响掌握度的测验或行为命令，在同一 PostgreSQL 事务内：

1. 验证 owner、幂等键、已发布资源版本和知识节点。
2. 在需要时对 owner + 节点的当前掌握度投影加行锁，追加一条证据。
3. 使用已固定的规则版本生成新 mastery revision，并以比较并交换或唯一约束替换当前投影。
4. 当已有路径的输入水位落后时，写入持久化的 `replan_required` 标记及触发 revision。

其中任一步失败则全部回滚，不得出现“有证据无掌握度”或反向的半完成状态。不影响掌握度的显式偏好仍使用证据事务，但不伪造 mastery revision。

### 画像更新

证据事务先独立提交。ProfileAgent 调用在事务外执行，再以“基础画像版本 + 证据水位”作乐观并发检查创建新版本。Provider 失败不回滚证据，也不创建空的或臆测的画像版本。并发冲突时重新读取最新版本，通过确定性合并规则重放，不使用最后写入者静默覆盖。

### 路径重算

路径规划不调用 Provider。它在单独的短事务中读取已提交的图谱、画像和掌握度版本，写入一个完整的新路径版本，再原子替换当前版本引用并清除对应 `replan_required` 标记。读取到的输入在提交前已变化时，本次结果不能成为当前路径，应使用新水位重试。

行为命令可以紧接着同步触发这个短路径事务，以在一次 API 响应中给出新推荐，但二者不伪装成一个长事务。如果进程在两个事务之间中断，持久化标记使重启后的读请求、重试或修复任务能够安全补算。客户端不得将过期路径标记为已根据最新证据更新。

## 并发、重复提交与服务重启

- 数据库唯一约束至少覆盖 `(owner_id, idempotency_key)`、画像 `(owner_id, version)`、掌握度 `(owner_id, node_id, revision)` 和路径 `(owner_id, goal_id, version)`。
- 同一 owner + 节点的掌握度更新串行化；不同 owner 或节点可并行。画像和当前路径使用基础版本进行乐观并发检查。
- 幂等命中不再评分、不重复追加证据、不再增加掌握度或路径版本。上一次仅完成证据/掌握度事务时，重试可补做带标记的路径重算。
- PostgreSQL 是唯一持久状态源。幂等记录、证据、版本、当前投影指针与待重规划标记不得只存进程内存。重启后从已提交的水位继续，不猜测中断事务已成功。

## 重算规则

1. 默认重算使用原版本记录的规则，必须得到相同结果；数值四舍五入、时间衰减基准时刻和排序求值均为规则的一部分。
2. 用新规则的迁移性重算必须由显式命令触发，创建新 revision/version，并记录 `recomputed_from`、新规则版本和原因。
3. 被补偿证据排除后，从该 owner + 节点的有效证据集重建掌握度；不从旧的可变当前分数继续累加。
4. 路径只依赖其记录的图谱、画像、掌握度水位和规则版本。任一输入变化均创建新路径版本，不修改旧版本。

## 替代方案

| 方案 | 不采用原因 |
| --- | --- |
| 只保存当前掌握分和画像 JSON | 无法审计、解释、幂等处理或应用新规则重算。 |
| 所有状态使用完整事件溯源 | MVP 0.2 查询和迁移复杂度过高；保留只追加事实 + 可重建投影已满足可追溯性。 |
| 让 LLM 直接输出掌握度和路径 | 结果不稳定、不可重算，且无法安全处理重复提交。 |
| 把 Provider 调用放入数据库事务 | 长时间占锁，且 Provider 失败会不必要地丢失已发生的学习事实。 |
| 证据、掌握度、画像和路径使用一个跨 Provider 长事务 | 无法将外部调用纳入 PostgreSQL 原子性，重试语义不清晰。 |

## 后果与后续实现约束

- T006/T007 需将画像事件与不可变画像快照分开，并实现确定性合并。
- T010–T014 需实现服务端评分、只追加证据、mastery revision/当前投影和命令事务。
- T016/T017 需为规划器固定配置版本、稳定求值、输入水位和持久化重规划标记。
- T002 的 API 契约必须暴露幂等冲突、版本冲突、路径新鲜度和去敏证据摘要，不接受客户端写入 owner、分数、掌握状态或规则版本。
