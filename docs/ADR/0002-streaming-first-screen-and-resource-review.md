# ADR-0002：流式首屏与正式资源审核时序

- 状态：部分批准（MVP 0.2-T030 最小恢复语义已批准；其余提案与待决项未整体批准）
- 日期：2026-09-16
- 关联任务：MVP-0.1-T002
- 关联需求：PRD §3.3、§7.7、§8.1、§10.4
- 审批依据：PRD 已规定首段流式展示、正式学习资源由 ReviewAgent 审核，以及 SSE 事件类型；未规定临时内容的留存、重连和审核并发细节，故这些细节仍为 Proposed；2026-09-27 的有限批准和后续计时决定见下文。

## 阅读与批准边界

- PRD 已确定：正式资源必须经 schema 与 ReviewAgent 后发布；未审核内容不能作为正式版本读取或导出。
- MVP 0.2-T030 仅批准本文“已批准的最小恢复语义”，不批准同操作新 attempt 重启或可靠进程中断识别。
- 下文双轨状态机保留设计提案；它不是所有分支已获批准或已经实现的声明。现行接口见 [OpenAPI](../api/openapi.yaml)。审核内部修正与终态操作重新启动是不同机制。
- 指标适用范围以本文更新后的计时说明和 [MVP 0.2 收尾决定](../acceptance/mvp-0.2-closeout-decision.md) 为准；历史采样与失败证据不回写。

## 背景

MVP 需要在用户用一句话发起学习后快速返回首段可学习内容，同时保证持久化的讲解、代码和练习在发布前通过 schema 校验与 ReviewAgent。若将审核置于首个 token 之前，审核模型的延迟会直接破坏“第一段可学习内容 P95 ≤ 10 秒”；若将未审核流直接保存或作为正式资源读取，则违反 PRD 的正式资源审核要求。

## 设计提案：临时流与正式版本双轨

首段讲解可作为**临时流内容**立即显示，但只能通过轻量运行时规则，不是正式资源，也不可作为可恢复、导出或共享版本。完整场景候选完成后，服务端在独立的审核路径中执行 schema 校验和 ReviewAgent；只有审核通过的不可变版本才成为正式资源并发出 `scene_ready`。

### 状态机

```text
accepted
  └─ preparing
       └─ streaming_temporary ── token* ──→ temporary_complete
                                                │
                                                ├─ schema_invalid / canceled / failed → terminal
                                                └─ reviewing
                                                     ├─ review_pass → published → scene_ready → done
                                                     ├─ review_reject (attempt < 2) → regenerating → reviewing
                                                     └─ review_reject (attempt = 2) / failed → terminal
```

- `accepted`：服务端已验证身份、请求 schema 和幂等键，并持久化学习会话/场景操作元数据。
- `streaming_temporary`：服务端以 `token` SSE 事件发送首段候选；每个事件先经过长度、内容类型、敏感内容和协议格式等轻量规则。浏览器可显示它，但不得把它标记为“已审核”或写入正式资源表。
- `temporary_complete`：完整候选生成结束；它可留在受限的操作工作区供审核，但不可通过资源读取 API、导出或新会话恢复直接访问。
- `reviewing`：先 schema 校验，再调用 ReviewAgent。审核拒绝时携带问题清单定向重生成，最多两次；每个候选保持独立 `attempt` 与内容摘要。
- `published`：原子写入正式资源版本、审核摘要和场景版本引用；事务提交后才发 `review_pass` 与 `scene_ready`。后续读取、导出和恢复只能使用此状态的版本。
- 持久化层以 `review_status='passed'` 且 `published_at` 非空识别正式资源；数据库约束禁止未审核发布，并拒绝已发布版本的原地更新。重新解释须创建新版本。
- `terminal`：失败、取消或审核重试耗尽。已发布的旧版本不受影响；任何未发布候选都不能被提升为正式版本。

## SSE 与持久化边界

1. `agent_start` 表示生成已开始；`token` 仅表示临时文本；`review_pass` 仅表示当前候选审核通过；`scene_ready` 才表示存在可读取的正式版本；`done` 表示本次操作终结。MVP 0.1-T003 是原提案中的事件契约任务；当前字段以 OpenAPI 为准，不由本段推定新增事件重放能力。
2. 依据 ADR-0001，操作状态、幂等键、当前阶段、尝试次数及已发布版本引用写入 PostgreSQL。暂存 token 和未审核正文可在服务重启或连接断开后丢失，且不得被恢复为正式资源。
3. 客户端在收到 `token` 时必须显示“生成中/待审核”语义；收到 `scene_ready` 后替换或标记为正式版本。断线期间不得把浏览器内存里的临时文本当作已完成学习资源。

## 恢复边界：现行契约与保留提案

| 情形 | 最小恢复策略 |
| --- | --- |
| SSE 连接断开 | 客户端保留操作 ID 并重新读取已持久化状态；若操作仍在运行，可重新附着到后续事件。临时 token 不保证回放；若已发布，读取正式版本。 |
| 服务重启 | 读取 PostgreSQL 已提交状态和已发布版本；临时流可丢失。当前没有可靠中断识别，未写终态的操作可能持续运行中。原提案的“识别中断后转失败”尚未批准和实现，不能通过查询或猜测超时触发。 |
| 同一请求重试 | 使用客户端提供的 `Idempotency-Key` 与匿名用户、请求摘要绑定。相同键返回同一操作/最终版本，不创建第二个学习单元或资源版本。 |
| 已失败或取消 | 同键仅恢复原终态；只有用户明确重新生成或提交新目标才换幂等键。原提案的“同一操作新 attempt 重启”未获本次批准，也未实现。 |
| 用户取消 | 现行 OpenAPI 定义持久化取消意图和幂等响应；原设计要求生成和审核在下一个安全检查点停止。已提交正式版本保留，未发布候选丢弃。重复取消为幂等成功。 |
| 用户重入/重新解释 | PRD 要求已发布场景保持不可变；当前场景重解释服务由 MVP 0.3-T021 实施。相同幂等键附着原操作；用户明确的重新解释创建新场景版本/新操作，不覆盖其他已完成场景。 |

这一定义不承诺在 POST `fetch` 流中精确回放断线前的每个 token；它承诺恢复操作状态与已审核版本。当前 API 契约保留这一限制，前端不得把临时内容当作已审核资源。

## 性能指标与已批准的测量说明

| 指标 | 目标与适用范围 |
| --- | --- |
| HTTP 首字节 | PRD §8.1：P95 ≤ 2 秒；不能用首个正文 token 代替 HTTP 首字节。 |
| 完整可学习首段 | PRD §8.1：P95 ≤ 10 秒；空白、心跳、状态事件和不完整字符不构成教学段落。 |
| 教学正文首 token | 独立观察目标 P95 ≤ 2 秒；MVP 0.2 实测 2632.575ms 未通过，已批准转后续非阻塞优化。 |
| 审核发布延迟 | 从候选完成到正式发布单独记录，不用首屏性能替代质量或生成成功率。 |

原提案将“服务端认证/schema 校验通过至首个有效 token 到达”称作 TTFB；此命名已被后续口径纠正。HTTP 首字节、教学首 token、完整首段必须分别记录，不可互换，也不能将某一计时起点套用到所有指标。

MVP 0.2 的实际起止点、正文资格和失败分母见 [T033 口径纠正](../acceptance/mvp-0.2-t033-nonbillable-diagnosis.md)、[T038 冻结计划](../acceptance/mvp-0.2-t038-frozen-plan.md) 和 [收尾决定](../acceptance/mvp-0.2-closeout-decision.md)。原始失败 gate 保留；Pro 质量/闭环与 Flash 性能不能拼成同一模型全项通过。

MVP 0.3-T001 需在新采样前冻结各指标的起止点、样本、失败处理和预算；本次文档整理不批准新采样。按 Provider、模型和请求类型分开报告；临时首段已显示但最终审核失败的操作不能计入正式资源生成成功。

## 替代方案

| 方案 | 不采用原因 |
| --- | --- |
| 首段发送前先完成 ReviewAgent 审核 | 将不可控审核延迟放入 10 秒首段路径，难以满足 PRD §8.1。 |
| 所有流式 token 直接保存为正式讲解 | 未通过 schema/ReviewAgent，违反 PRD §3.3 与 §8.2。 |
| 断线后只依赖浏览器缓存恢复全文 | 服务重启和跨标签页不可靠，且客户端缓存可能把未审核内容伪装为正式版本。 |
| 断线后无条件重新生成 | 会产生重复资源、浪费 Provider 调用，并违背场景版本可恢复与幂等要求。 |

## 待决项与审批请求

### MVP 0.2 T030 已批准的最小恢复语义（2026-09-27）

用户批准本次修复采用以下有限契约；不表示批准本文其他 Proposed 项，也不新增同操作 attempt 重启机制：

- 操作 GET 只读取 owner 隔离的持久化状态，不能因为客户端断线或一次查询就把运行中任务写成失败。
- 网络重试保留目标、操作 ID 和幂等键。已知操作优先 GET，已发布读取原单元；运行中等待后再次查询，不触发 Provider。
- 尚未取得操作 ID 时，原目标加原幂等键 POST 可重放身份；相同键的失败也仅回放，不重启生成或增加 attempt。
- 已失败/取消时，恢复展示终态；只有用户明确选择新一轮生成或提交新目标才换幂等键。
- 当前未实现可靠的进程中断识别。真正中断且未写终态的操作可能持续显示运行中；本次不以猜测超时代替存活判据。

1. 临时首段在审核最终拒绝时的产品呈现：默认提议为显示“该版本未通过审核，已移除”，而不将它保留为可继续学习的内容。
2. 当前 OpenAPI 已定义 `GET /api/learning-operations/{operationId}/events`，仅订阅连接建立后的事件；持久化事件保留窗口及 `Last-Event-ID` 重放保证仍待确定，不能声称临时 token 完整回放。MVP 0.3 Job SSE 契约需单独制定。
3. ReviewAgent 不可用时，临时内容是否仍允许继续展示及如何提示仍待确定；正式内容不得绕过审核发布已经由 PRD 确定，无需重新批准该门禁。
4. 取消已进入 Provider 调用的成本处理和最长执行时限，需要 Provider Gateway 任务的错误与超时策略批准。

这些项目影响可见内容的可信语义、恢复承诺或成本控制；在批准前，后续实现不得把临时流提升为正式版本，也不得宣称 token 可完全回放。

## 后果

- 后端需要为学习场景操作保存可恢复的阶段、幂等键、attempt、取消标志和正式版本引用；实现时不得将未审核正文暴露为资源读取结果。
- 前端需要区分“生成中/待审核”和“已审核正式版本”，并在断线后恢复操作状态而非假装已收到完整流。
- MVP 0.1-T003/T004 是本 ADR 起草时的接口/骨架任务；当前实现依据已批准的有限契约与 OpenAPI。新契约不得将本文提案中的未批准分支直接视为现行能力。
