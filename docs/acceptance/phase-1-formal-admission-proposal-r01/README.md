# T040 正式验收准入提案 r01

状态：**零调用提案，待评审；不可执行，新增真实调用授权为0。** 日期：2026-10-20。用户已确认采用“分项计分＋按影响分级停止”；本文件提出具体样本、上限与实施门禁，尚不代表这些细则或真实预算获批。

## 1. 本次要作出的决定

保留当前生成 deepseek-flash/none、审核 gpt-6-luna/high、v4.9 Prompt/业务 Schema/传输投影与路由。审核8192总输出、单调用60秒、connect5秒不变；计划2048、资源生成/修正4096，温度0。Base URL与路由证据见[配置与预算](proposal.json)，不修改生产默认或 `.env`。

只提出**一个正式验收方案**：先完成零调用准入，随后在同一个新冻结包中，先运行50份正式审核基准；达到门槛后才运行100个正式生成目标。没有再加一轮反复调参的小诊断，没有第二个候选或失败后再试一轮。当前只准备提案，不制作虚假的可执行包或预签材料。

原第4条的[附带修复错误](../phase-1-review-continuation-r01/results/holdout-stack-safety.md)与[原样复测符合预期](../phase-1-review-stack-recurrence-r01/results/holdout-stack-safety.md)同时封存。原样复测不证明修复或稳定，不改变原轮退出；旧样本只作历史审计，不进入正式分母，不再追求连续通过。

## 2. 分项计分：拒绝命中不等于整例正确

所有实际回答逐项核对 `findings`、`impact`、`unresolved` 和每个主辅引用；不能只看 verdict。每条记录并列保存：

| 字段 | 计分规则 |
| --- | --- |
| 技术完整性 | HTTP、模型/推理请求、完整输出、完整业务Schema、必检项、准确wire、用量分别记录；失败/未知不能记0用量或移出分母 |
| 核心缺陷检出 | 具体定位预先标注的严重缺陷才记命中；单纯reject或needs_human不记命中 |
| 分类 | 已具体检出且类别正确才计；仍以原20份严重错误为分母 |
| 附带断言 | 每条主张都须有证据；错误建议、过强结论、虚构要求、错误证据声明均记录，不因核心拒绝正确被隐藏 |
| 引用 | 每个锚点必须支持所引用的具体命题；仅字段相关不足，不能借邻近字段；无引用不是引用能力通过 |
| 完整审核质量 | 本例各适用scope的预期结论、全部断言与引用都正确才通过；任何附带实质错误，本例此项失败 |
| 影响 | 单列是否误放行、误阻发布、误转人工、错误进入或拟进入自动修正、修正后引入/保留缺陷；附实际路由/版本证据 |

第4条若出现在新正式集：严重缺陷检出可以记命中、分类可以正确；附带断言与完整审核质量仍失败。不得把它算成“整例通过”，也不得反过来伪造“未检出越界”。此规则仅用于新冻结方案，不重算旧分数。

## 3. 分级停止：何时停样本，何时停整轮

所有结果均留在仅验收可见的隔离环境，正式验收不向用户发布课程、不开放dynamic。隔离不等于可以容忍错误修正指令。

| 级别 | 可核查事件 | 动作 |
| --- | --- | --- |
| 红：立即停止整轮 | 某scope实际包含预标严重缺陷，却被该scope审核判pass，或含严重缺陷的单元最终取得自动发布资格；无据严重错误导致错误硬拒绝；错误审核指令进入或按实际路由即将进入自动修正；修正引入/保留严重缺陷却被自动放行；跨owner/泄漏/发布隔离或硬门禁失效；模型/路由/配置改变；超预算或发送状态不确定 | 发现即停，不再发新请求，取消未发槽；冻结失败和未运行项，不换模型、改Prompt、补样本或重开预算 |
| 黄：隔离失败，继续冻结样本 | 核心严重拒绝正确，附带错误仅留在不参与修正的诊断说明中；非严重误拒/不必要转人工；严重缺陷没有具体检出但仍被隔离且不会自动放行；单次明确无发布风险的格式/截断/Schema失败 | 本例相应指标失败、不发布、不修正；完成核对后可以继续不同的剩余冻结材料，不能重复本例或修到通过 |
| 绿 | 结论、全部主张/引用及路由均符合冻结标签 | 记录后继续，不用通过样本抵销历史失败 |

scope须按预先独立标签判定：例如严重缺陷仅在代码，讲解与练习没有该缺陷，它们各自正确pass不触发红停。不得要求无缺陷scope替其他scope拒绝。

“错误进入修正”须核查**发给生成器的实际上下文**，不能凭文字像建议就认定已传播；反之，只要错误finding将按实际 `revise` 路由被消费，就不能当成无害说明继续。当前单元级reject无自动整单元修正，资源级revise会传递findings，依据[资源审核](../../../backend/app/agents/hybrid_resource_review.py)、[单元审核](../../../backend/app/agents/unit_consistency_review.py)与[正式流程](../../../backend/app/services/planned_learning_flow.py)。

**修正前检查时点：**执行包必须在现有 `on_review` 回调中持久记录每次资源revise，并由实际验收审核人核对完整候选、全部findings和待发修正上下文，再允许原样发送。不能先自动修完、事后评分却声称阻止了传播。错误或证据不足时不发送下一模型请求；发现错误按红级停止，证据不足保持暂停核清。等待、数据库提交和核对都在该操作原180秒绝对期限内，不能停表或重置；时间耗尽则该目标失败、不得修正/重发。如已发现错误，超时也不能把红级降成普通失败。审核人只记录验收评分，不给生成器补提示、修内容或改路由；发生人类介入纠错的目标不得计自动成功。这个验收观察门禁不自动加入生产配置；观察次数、人工耗时、超时和阻断情况必须单列，不能只引用自动成功率而省略该实验条件，也不能据此声称生产已经实现自动语义拦截。没有能实际承担即时revise核对的审核人，不启动本轮。

已明确收到且可隔离的技术失败按黄级保留；连接/整次超时若不能确定发送或接收状态，则按红级停止，未知用量不清零。无自动传输重试或隐式回退。停止后的未运行项仍列在冻结总分母中；报告“本轮中止/未完成”，不得凭已运行子集宣称通过，也不把未运行伪称为观察到的模型错误。

当只出现黄级而最终阈值已不可能达标，仍可在原授权上限内完成剩余独立样本，以免按是否成功选择性截断频率统计；最终必须判失败。不是追加请求、重复取最好答案或改判阈值。

## 5. 具体准入与验收门槛（本节待用户批准）

原98%/95%/90%门槛不降低；本提案额外提出低风险附带错误的严格容许上限。分项统计不意味着自动容忍。

| 指标 | 要求与固定分母 |
| --- | --- |
| A unit首次完整Schema | ≥49/50；200个不同scope回答的首次结构有效率另报，不混作生成目标的98/100 |
| A严重检出/分类 | unit具体严重召回≥18/20、分类准确≥18/20；严重错误auto-pass为红级，出现一次整轮中止，即使主召回比例仍可能达90% |
| A正确对照 | ≥19/20个材料的3资源及unit均自动pass且内容/审核意见正确；人工通过不补分，scope失败不能用另一scope成功覆盖 |
| A长审核 | 10/10个unit完整且Schema有效；预期pass或needs_human按冻结标签另外判断，完整不代表语义正确 |
| A完整审核质量 | ≥48/50材料的全部适用scope结论、断言与引用正确；4次回答不增加材料分母 |
| **A低风险附带错误** | **错误断言或错误引用的材料并集最多1/50（2%）**，且只能是黄级。每条实质错误仍使该材料完整质量失败；多个scope/多个错误逐项保留，不能分别各容许1例。这个2%是新增提议，不是既有批准或统计结论 |
| B首次生成Schema | ≥98/100：计划和三类首候选都有效才计，修正不回填 |
| B自动正式成功 | ≥95/100：本地资格、三资源与unit审核自动通过，独立人工核对实际内容及全部审核意见正确，并通过隔离原子发布验证；任一实质附带错误使该目标不能计成功，不等于内容被真实发布 |
| B修正与发布安全 | 全部资源revise记录原发现、实际修正输入、新旧内容digest/差异、重新审核、后序失效重建；错误被传播或硬门禁失守触发红级。未发生真实修正时只能报告“未观察到”，不能用Mock宣称此链路质量验收完毕 |
| B附带错误 | 逐目标、逐次回答、逐断言/引用分别报告；完整质量要求已计入≥95/100，最多5个失败名额不豁免任何红级事件。自动成功不能隐藏中间审核/修正的实质错误 |
| C门禁 | 固定20/20通过，未运行或环境不可用不是通过；真实PG/隔离发布实现验证缺失则不准入 |

这些比例是固定分层基准上的描述性结果，不是实际用户总体错误率或复发概率。报告每个分层/节点/family及stage/scope的分子分母；输出过长导致断言较多时，断言级比例只能作为补充，不能稀释材料级失败。样本按覆盖构建且可能相关，不据此给出假设独立随机样本的总体置信保证。

报告同时保存技术完整/核心命中/完整质量/附带错误/人工依赖/实际路由影响。模型自动pass不等于事实正确，真实人工评分只作验收依据；产品人工批准是另一件事。两种人工角色分开登记，不伪签。B真实修正覆盖最低要求：至少一次explanation或code资源的完整revise→原样finding输入→新候选→复审→后续资源按新digest生成，以及至少一次exercise资源的同类修正。两轮耗尽、已有后序资源失效重建用C的合成结果/实际PG工程回归验证，不伪称初次串行生成能实测所有重解释路径。真实修正只按实际发生报告，不通过注入旧错误或人造revise凑覆盖；未自然满足上述覆盖时，A/B对审核本身可计分，但“修正链路影响”仍未覆盖，T040整体不能宣称全部完成，另行讨论缺口，不临时补发新请求。

## 6. 精确请求上界与预算边界

| 部分 | 正常无修正 | 最坏调用数 | 最坏生成/审核 |
| --- | ---: | ---: | --- |
| A 50×4 | 200 | 200 | 0生成、200审核 |
| B 100目标 | 800 | 2000 | 1000生成（含计划）、1000审核 |
| 合计 | **1000** | **2200** | **1000生成、1200审核** |

B每目标最多：计划1＋三类初生成3＋修正生成6＋资源审核9＋unit审核1＝20。正常8次不是600旧链路口径；20/180秒是上界，不保证来得及跑满。无临时画像/临时流，故不使用22上界。拒绝、失败、发送未知、修正、取消前已发请求均消耗独立槽；0传输重试/隐式回退，unused槽不转用途。本方案不含额外兼容探测或诊断API请求。

总输出上界（均含推理，不是预计实际用量）：

- 100计划×2048＝204,800。
- 900资源初生成/修正×4096＝3,686,400。
- 1200审核×8192＝9,830,400。
- **合计13,721,600输出tokens**，每角色和全局双重预留，不以实际输出较少放出额外请求。

单次60秒、HTTP connect5秒及最多5秒清理保持。A 200×60秒和B 100×180秒的运行窗口保守合计30,000秒（8小时20分），清理另保守预留最多2200×5秒；这是上界而非耗时承诺，人工/数据库时间不能通过重置操作180秒期限隐藏。全轮自首次预约起7天含人工评分，届满停止，不续时。

费用沿用用户“不用考虑费用，无上限”：金额cap=null，渠道单价/币种未提供，不冒用官方价格。**2200次/输出上界不等于实际输入＋输出总量**；输入依赖冻结材料和已生成父结果。准确输入token上界、最大请求字节、渠道上下文约束与子请求信封核验尚未完成，必须在可执行包批准前形成实际证据；不能用UTF-8字节冒充token，也不能将本提案当作已有完整费用证明。所有usage和账单未知项保留未知，历史未知超时不记0、不转新预算。

原ADR-0015的审核2048输出基线与当前候选8192不同：8192已在候选诊断实接，但不因此自动授权正式2200请求。正式包须明确批准此次有界审核上限及分级停止细则；不改业务Prompt/Schema/生产默认，不扩展旧轮授权。
