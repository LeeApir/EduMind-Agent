# 计划错误与待人工闭环审计 r01（零真实调用）

结论：**当前机制已能把本次问题课程挡在正式发布之外，但没有自动修复计划错误的闭环。** 现有资源有限修正不等于计划纠错；待人工是一种安全停靠状态，不自动等于错误已被解决。此次只核查并提出边界，不改生产Prompt、Schema、持久化模型或业务实现。

本次新留出输入见 [H01–H08核对表](../phase-1-holdout-reserve-r01/README.md)。Lee已答复“我本人核对”，只登记独立验收标签复核分工，没有签核内容，也没有批准任何产品待审课程。A/G及12类对照仍为开发回归。

## 机制缺口（源码核对）

1. **计划只有结构/绑定校验，没有独立的前置语义纠错门。** `generate_shared_plan`绑定受信元数据，`validate_plan`检查Schema、引用和节点；计划obj写17而自身轨迹19这样的语义冲突仍可进入后续生成。`run_planned_operation`创建/保存计划后立即构造三个场景，不执行独立计划语义检查或计划重试。
2. **资源修正保持原计划。** `review_resource`只让当前资源重新生成，明确指令`Preserve plan conventions`；计划对象/摘要不变。计划问题若被模型误报为资源revise，反馈也会送到该资源纠错器，系统没有受信的“错误来自计划”路由字段。回放显示这种反馈仍走正文修正，不是证明实际模型必定如此，也不把无据修正意见当真值。
3. **单元审核不是全局修复器。** unit只允许pass/reject/needs_human；revise是协议错误，没有自动全单元重生成循环。纯覆盖不足/证据不足进入needs_human是正确边界，但不会自动补齐题目。
4. **人工是在看固定版本，不是在编辑课程。** `decide_case`仅approve/reject；签核绑定准确case_digest，不更改计划、题目或审核历史。approve对语义正确性信任维护人，硬校验不能证明所有自由文本计划结论正确；已确认计划错误不得靠一句理由approve。拒绝后需显式新操作/版本，没有定向退回计划、编辑建议及闭环重建的专用接口。
5. **当前人工案件需要完整单元。** `create_review_case`要求完整material和4份最终审核；计划阶段只有半份材料不能直接复用它。因此在计划早期转人工，涉及新的案件/状态/展示契约，不能只加一个needs_human分支。
6. **人工视图未展示全部修正历史。** 数据库通过persist_review保存各次审核，但CLI `show --body/--export`只按case.payload.review_ids查询四份最终记录。ADR-0015要求复核完整发现与修正记录；现在的CLI视图不足以核对早期无据反馈是否影响最终内容。需要完整操作历史/候选前后摘要及最终记录标识；尚未修改。
7. **“重新生成/换示例”不是待审计划修复。** Web重新生成开启新请求，没有结构化修复指令或旧案解决关系；重试恢复也不发新生成。`planned_reexplanation`换示例虽能生成新计划，但先要求已有正式publication，不能拿它修复尚未发布的本次案件。不能保证重跑相同原文就不复发。是否有旧待审案遗留/如何关联新请求还需专门的跨新请求集成验收，不能从按钮存在推断已解决。
8. **缺陷字段未提供计划级证据与修复目标。** findings锚点指向资源，scope只有resource/unit；unresolved是自由文本。不能可靠地自动区分计划错误、用户要求矛盾、正文错误或审核误归因。仅按关键词“计划”“缺题”触发重生会再次混淆来源。

严重错误的本地阻断也有边界：route_review依赖模型verdict和具体证据完整性，不独立证明任意C行为或审核语义。severity字段不等于可信事实，不能简单将severe自动映射拒绝来掩盖模型误报；有据严重缺陷必须阻断，仍需要可靠检出和人工判断。

## 自动/人工处理边界

| 问题 | 当前处理与自动上限 | 应采用的边界 / 需补的能力 |
| --- | --- | --- |
| 已知计划正确，当前资源存在定位明确、证据成立的局部错误，模型resource revise | 当前最多2次正文修正，每次完整资源重审；未过转人工或拒绝 | 可保留有限自动修正；不能改原始目标/计划约定/安全前提；反馈无据则停，不向正文传播 |
| 过程已教，但明确要求的过程题或测量缺失 | 常为needs_human，无自动补题；unit不支持revise | 可考虑未来受约束补题，但必须先确认原始要求/已验证计划和缺口，仅改变相关资源并使后序依赖失效、全部重审；不能伪装成fact来借用修正分支 |
| 原文无歧义，模型计划出现可独立复现的内部矛盾 | 当前needs_human/失败，无计划自动修复 | **当前不自动修计划**。未来仅在有可信证据、明确字段/来源和局部可修复范围时，允许最多1次新计划候选重建；拒绝原地改已绑定计划，所有旧内容/审核/案件失效后重建与重审。没有证据或再次失败交人工 |
| 用户本身要求矛盾、目标主次不明、需要改变范围/示例 | 不能推测用户意图 | 必须由用户澄清，保留原请求并明确新版本；维护人不能替学生改变目标后称原要求已满足 |
| 附件/外部正文/作用域/调用条件缺失，事实不可判 | needs_human | 必须补材料/人工判定，不能从无法保证P推出非P，不自动编造前提再修 |
| 审核把模型计划冒称用户要求、引用不支持结论、反馈本身可疑 | 当前可能待人工，也可能模型自信误拒 | 先人工核对原文/引用和错误出处；不得把可疑意见直接送资源修正器。重新审核仍需独立预算，不反复试到pass |
| 确认的可达严重安全/事实缺陷 | 模型reject或本地硬规则阻断 | 原候选禁止发布，人工也不得“批准忽略”；确需修复用新候选/操作重新校验。不用未知项将严重错误整体降级 |
| Schema/身份/版本/沙箱/预算失败，Provider超时等技术故障 | failed/拒绝，不发布；无自动重试/回退 | 不交人工作质量旁路，不隐藏失败重开预算；显式新操作须另获准确授权 |
| 两次局部修正仍失败、一次拟议计划重建仍失败或剩余预算不足 | 当前资源修正耗尽转人工；无计划重建 | 停止自动处理，完整交接原因/所有历史，不追加无限修复轮 |

资源级有据fact问题是否能在同一操作有限修正，取决于有效verdict及修复范围；已reject不能自动降成revise。表中的“阻断”首先指原候选不得发布，不能仅靠severity文字决定事实真伪或跳过现有路由。

上述计划重建/受约束补题只是**候选设计，不是已实现或已批准的新行为**。不能先在生成/审核Prompt中临时模拟它们，绕过状态和版本设计。

## 建议下一决策顺序

1. 先补齐人工只读视图的完整审核/修正历史和最终候选对应关系，使人工能看清问题；它修复既定ADR要求，不代表已有修改权限或本次已实施。
2. 设计“原始要求→计划承诺→学生内容”的类型化缺陷定位：错误层级、字段/摘要、依据来源、具体反例、可判定/缺信息及允许的修复范围。复用开发四类回归，不接触H留出标签做调优。
3. 在内容生成前检查计划；真正计划错误只生成一个新计划候选。缺信息/范围决策送用户或维护人，不能把错误计划继续当修正目标。若前置人工发生在完整单元之前，另设计案件契约；不要向现有完整单元案件塞半成品。
4. 新计划版本必须使旧资源/审核/待审案失效并全部重建，不可沿用旧pass；现有版本校验可复用，但完整修复闭环仍需实现和验证。
5. 先重算调用预算/截止再批准实现方案。现有操作绝对180秒、持久上限20次，API中可选目标映射也占同一额度；新增计划检查/重建不能暗加请求、重置时钟或仍声称原8次基线。若不调整20上限，就必须收紧共享资源修正槽；具体计数须随执行设计冻结。

是否改实现应在这份边界及具体契约/任务获准后决定。本次没有创建“计划自动修好”的成功提交，没有调用模型、给真实案件签核、重开旧预算或改变生产逻辑。正式质量与T040仍blocked。

## 人工的三种身份不可混用

- Lee核对H预标签：验收数据标注，不发布课程。
- 受信维护CLI复核固定产品案件：真实语义approve/reject，受本机allowlist与摘要约束，不自动改分或编辑内容。
- 学生澄清原教学要求：决定需求，不是模型/维护人代替决定。
