# 新审核表示及预约原型：开发中

本记录不是冻结、验收或真实执行授权。旧 [T101 冻结闭包](../phase-1.5-teaching-frozen-r01/README.md) 不变；本记录的版本、4 MiB 请求上限、指令和 `bytes + 8192` 本地输入预约均为新开发候选，尚未证明覆盖全部合法输入，也不能保证服务端上下文或费用上限。

`scripts/isolated_diagnostics/p15_review_path_v2.py` 完整发送候选和参考，将目标目录从重复文本改为目标 ID → JSON Pointer。构造时重建并核验每个目标的路径、值和摘要；响应验证重建准确请求及原始 binding 后沿用严格审核 Schema 和引用检查。候选还从原始输出和规格重建，拒绝 source 被篡改后再重算摘要的情况。审查定位可通过路径找回内容，但完整 artifact 内部 raw_output/source 和参考之间仍有重复；摘要自洽仍不能证明 Provider 来源，真实控制器须以受控原始响应重建。

开发测试使用最长 3+4 规格，B/C 同规格、8 段、四题及较长字段；B 64 状态/180 动作，构造首版和绑定其摘要的修订版，另测试转义、遗漏、错位和篡改。一次试验 B 首版/修订 283,880/299,944 字节，C 173,139/189,267 字节。这些是合成样例，不证明全空间上界；构造的父摘要也不证明来自真实回包及收据。缺少对 128,000 字节原 payload、最坏 JSON 转义及极限引用放大的上界分析。

`scripts/isolated_diagnostics/p15_reservation_v2.py` 只是离线 SQLite 预约试验：先记本地预约、发送标记、结算/unknown 占额。独立复核发现它尚不具备可用于真实控制器的安全边界：文件/父目录及并发别名校验、固定槽位/臂/阶段/包授权、重复请求拒绝、发送与停止的排他围栏、真实响应来源和失败自动停止均未完整实现。现有 `settle` 接受调用者传入的数字，不证明 Provider 用量。禁止把它作为可执行包或用于真实发送。

下一步应先完成容量上界和独立复核，增强持久账本及真实 Responses 执行状态机；用将来真实使用的控制器配合 Mock HTTP 跑通逐槽预约、发送、响应、候选、审核、一次修复和重审，测试错父版、超限、unknown 和停止后不得发送。完成后交独立评估，再冻结完整新执行器和策略，随后独立选样及准备准确包。本轮无真实调用。
