## 已确认关键路径

实际链：匿名用户/会话落库 → POST Cookie/CSRF及用户DB读取 → 操作幂等预留 →
显式目标别名（必要时模型识别）→ 画像提取Provider → owner锁下合并画像并落库 →
画像提交 → owner锁下读取画像/掌握度，计算前置路径并提交 → HTTP/SSE状态 →
操作状态读取/更新 → Provider文本流 → 审核状态 → 正式生成/审核/发布。

诊断走真实应用函数和隔离PG，Provider全部FakeAdapter，人工注入画像80ms、首delta25ms、
正式结构化每次5ms。首屏关键顺序由断言验证，非猜测厂商慢。
实际时段见mvp-0.2-t033-diagnostics-v2.json（纳秒同机单调时钟）：

上表是mock控制实验，不是真实模型时延，也不是客户端网络到达时刻。
诊断span可能嵌套，不能直接相加。v1记录的headers_sent被同键回放覆盖，
v2修正为原POST送出记录并按learning/same_key_replay区分；v1保留，不使用其头时刻作结论。
后续补充DB状态阶段的v3是新增观测，不能改写v2表。

生产数据库dependency当前每个请求创建/销毁engine；FastAPI0.115.12的yield清理发生在
流式响应消费之前。流体还使用同一factory，可能重新建立连接池与物理连接；
这解释了状态发送到文本请求之前仍有DB等待的代码路径，但真实冷连接占比尚无数据。
T034只优化应用lifespan内连接复用，用可控连接延迟验证，不声称消除画像Provider瓶颈。
图谱已lru_cache，不是每请求重新读YAML；不会添加无依据的重复缓存。

不能直接后台化或跳过画像：path_versions读取合并后的engineering_preference及profile_version，
已批准的显式修正要保留；若改变此顺序需决定首段/路径使用哪个画像版本、修正冲突处理、
失败和发布绑定语义。此部分未实施，也未自动改PRD/数据契约。

## 多候选与证据

first_screen_v2.py逐增量字符记录非空首字符时间；真正空行（含跨chunk/空白行）或
stage_changed/reviewing为批准边界；标题、围栏排除，不在半个空白行或异常EOF提前结束。
每个候选独立ID、SHA256、首字符/完整边界时刻、标点资格。内容语义由独立hash绑定的
人工decision（teaching/intro/unconfirmed加理由）判断；未评审的早期候选不能悄悄跳过。
intro明确否决后可选择后面的教学段落，并使用后段原始token/完成时刻，而非评审时刻。
缺标点、只有导语、超时、中断均保留未确认/错误，不当成功。任意token指标也保留以便排查。
默认不导出正文；只对固定公开基准目标的全新匿名用户允许候选段落正文，不存原始HTTP
头/body、Cookie/CSRF/Provider凭据、画像或完整模型流；代码围栏不出现在候选证据。

raw_learning_post通过loopback HTTP/1.1实际socket记录首响应字节，再收齐headers、解码
chunked SSE；测试故意先发H、延迟20ms再补全headers、再延迟20ms发状态，证明三者独立。
run_first_screen_v2.py是下一轮有界采样入口，本轮未执行；真实入口要求显式计费参数、
空账本240硬上限、20样本、单并发0预热180s，不覆盖历史、不客户端重试或补跑。
本轮只运行tests/test_first_screen_v2.py等offline测试；raw socket测试服务只产生公开fixture。
